## तपाईंले के सिक्नुहुनेछ

अहिलेसम्म तपाईंले एआईसँग कसरी कुराकानी गर्ने, प्रभावकारी रूपमा प्रॉम्प्ट कसरी निर्माण गर्ने, र प्रतिक्रियाहरूलाई तपाईंका कागजातहरूमा कसरी आधार गर्ने सिक्नुभयो। तर अझै एउटा आधारभूत सिमाना छ: भाषा मोडेलहरूले मात्र पाठ उत्पादन गर्न सक्छन्। तिनीहरू मौसम जाँच गर्न, गणना गर्न, डेटा बेस सोध्न वा बाह्य प्रणालीहरूसँग अन्तरक्रिया गर्न सक्दैनन्।

उपकरणहरूले यसलाई परिवर्तन गर्छन्। मोडेललाई कल गर्न सकिने कार्यहरू उपलब्ध गराएर, तपाईं यसलाई पाठ उत्पादन गर्ने यन्त्रबाट कार्य गर्न सक्ने एजेन्टमा परिणत गर्नुहुन्छ। मोडेलले कहिले उपकरण चाहिन्छ, कुन उपकरण प्रयोग गर्ने, र कुन प्यारामिटरहरू पास गर्ने निर्णय गर्छ। तपाईंको कोडले त्यो कार्य सञ्चालन गर्छ र नतिजा फर्काउँछ। मोडेल त्यो नतिजा आफ्नो प्रतिक्रियामा समावेश गर्छ।

## उपकरणहरूसँग एआई एजेन्टहरू बुझ्न

> **📝 नोट:** यस मोड्युलमा "एजेन्टहरू" भनी जनाइएको छ एआई सहायकहरूलाई जसले उपकरण कल गर्ने क्षमता वृद्धि गरिएको छ। यो [मोड्युल ०५: MCP](../05-mcp/README.md) मा समेटिने **एजेन्सिक AI** ढाँचाहरू (स्वायत्त एजेन्टहरू जसमा योजना, सम्झना, र बहु-चरण तर्क हुन्छ) भन्दा फरक छ।

उपकरण बिना, भाषा मोडेलले केवल यसको प्रशिक्षण डेटाबाट पाठ मात्र उत्पादन गर्न सक्छ। वर्तमान मौसम सोध्नुहोस्, र त्यसले केवल अनुमान लगाउँछ। उपकरणहरू उपलब्ध गराउँदा, यसले मौसम API कल गर्न सक्छ, गणना गर्न सक्छ वा डेटाबेस सोध्न सक्छ — अनि ती वास्तविक नतिजाहरू आफ्ना प्रतिक्रियामा जोड्न सक्छ।

<img src="../../../translated_images/ne/what-are-tools.724e468fc4de64da.webp" alt="Without Tools vs With Tools" width="800"/>

*उपकरण बिना मोडेलले मात्र अनुमान लगाउँछ — उपकरणहरूसँग यो API कल गर्न, गणना गर्न र वास्तविक-समय डेटा फिर्ता गर्न सक्छ।*

उपकरण भएको एआई एजेन्टले **तर्क र कार्य (ReAct)** ढाँचा अनुसरण गर्छ। मोडेलले मात्र जवाफ दिँदैन — यसले के चाहिन्छ भनी सोच्छ, उपकरण कल गरेर कार्य गर्छ, नतिजा अवलोकन गर्छ, अनि फेरि कार्य गर्ने वा अन्तिम उत्तर दिने निर्णय गर्छ:

1. **तर्क गर्नुहोस्** — एजेन्ट प्रयोगकर्ताको प्रश्न विश्लेषण गर्छ र के सूचना चाहिन्छ निर्धारण गर्छ
2. **कार्य गर्नुहोस्** — एजेन्ट सही उपकरण छान्छ, सहि प्यारामिटरहरू उत्पादन गर्छ, र कल गर्छ
3. **अवलोकन गर्नुहोस्** — एजेन्टले उपकरणबाट प्राप्त नतिजा पाउँछ र मूल्याङ्कन गर्छ
4. **दोहर्याउनुहोस् वा प्रतिक्रिया दिनुहोस्** — यदि थप डाटा चाहिन्छ भने पुनः लूप हुन्छ; नभए, प्राकृतिक भाषा जवाफ तयार गर्छ

<img src="../../../translated_images/ne/react-pattern-detail.96a5efeeb6dd2f61.webp" alt="ReAct Pattern" width="800"/>

*ReAct चक्र — एजेन्टले के गर्ने भनी तर्क गर्छ, उपकरण कल गरेर कार्य गर्छ, नतिजा अवलोकन गर्छ, र अन्तिम उत्तर दिन लूप गर्दै जान्छ।*

यसले स्वचालित रूपमा हुन्छ। तपाईंले उपकरणहरू र तिनका विवरणहरू परिभाषित गर्नुहुन्छ। मोडेलले कहिले र कसरी प्रयोग गर्ने निर्णय गर्छ।

## उपकरण कल कसरी काम गर्छ

### उपकरण परिभाषाहरू

[WeatherTool.java](../../../04-tools/src/main/java/com/example/langchain4j/agents/tools/WeatherTool.java) | [TemperatureTool.java](../../../04-tools/src/main/java/com/example/langchain4j/agents/tools/TemperatureTool.java)

तपाईं स्पष्ट विवरणहरू र प्यारामिटर निर्दिष्टहरूसँग कार्यहरू परिभाषित गर्नुहुन्छ। मोडेलले यी विवरणहरू सिस्टम प्रॉम्प्टमा हेर्छ र बुझ्छ कि प्रत्येक उपकरण के गर्छ।

```java
@Component
public class WeatherTool {
    
    @Tool("Get the current weather for a location")
    public String getCurrentWeather(@P("Location name") String location) {
        // तपाईंको मौसम खोज्ने तर्क
        return "Weather in " + location + ": 22°C, cloudy";
    }
}

@AiService
public interface Assistant {
    String chat(@MemoryId String sessionId, @UserMessage String message);
}

// असिस्टेन्ट स्वचालित रूपमा Spring Boot द्वारा जोडिएको छ:
// - ChatModel बीन
// - @Component वर्गहरूबाट सबै @Tool विधिहरू
// - सत्र व्यवस्थापनको लागि ChatMemoryProvider
```

तलको चित्रले प्रत्येक एनोटेशनलाई तोड्छ र देखाउँछ कसरी प्रत्येक भागले एआईलाई उपकरण कहिले कल गर्ने र के तर्कहरू पास गर्ने बुझ्न सहयोग गर्छ:

<img src="../../../translated_images/ne/tool-definitions-anatomy.f6468546037cf28b.webp" alt="Anatomy of Tool Definitions" width="800"/>

*उपकरण परिभाषाको संरचना — @Tool ले एआईलाई कहिले प्रयोग गर्ने बताउँछ, @P प्रत्येक प्यारामिटरको विवरण दिन्छ, र @AiService सबैलाई सुरुमा जोड्छ।*

> - "मक डाटा सट्टा वास्तविक OpenWeatherMap जस्तो वास्तविक मौसम API कसरी समावेश गर्ने?"
> - "एआईलाई सहि तरिकाले प्रयोग गर्न मद्दत गर्ने राम्रो उपकरण विवरण के हो?"
> - "उपकरण कार्यान्वयनमा API त्रुटि र दर सीमाहरू कसरी ह्यान्डल गर्ने?"

### निर्णय लिनु

जब प्रयोगकर्ताले "सिएटलमा मौसम कस्तो छ?" भन्छ, मोडेलले मनमानी रूपमा उपकरण छान्दैन। यसले प्रयोगकर्ताको अभिप्राय प्रत्येक उपकरण विवरणसँग तुलना गर्छ, सम्बन्धितताको आधारमा स्कोर गर्छ, र सबैभन्दा उपयुक्त छान्छ। त्यसपछि सही प्यारामिटरहरू सहित संरचित कार्य कल सिर्जना गर्छ — यस अवस्थामा, `location` लाई `"Seattle"` सेट गरेर।

यदि कुनै उपकरण प्रयोगकर्ताको अनुरोधसँग मेल खाँदैन भने, मोडेल आफ्नै ज्ञानबाट जवाफ दिन्छ। यदि धेरै उपकरण मेल खान्छ भने, सबैभन्दा विशिष्ट उपकरण चयन गरिन्छ।

<img src="../../../translated_images/ne/decision-making.409cd562e5cecc49.webp" alt="How the AI Decides Which Tool to Use" width="800"/>

*मोडेलले उपलब्ध प्रत्येक उपकरणलाई प्रयोगकर्ताको अभिप्रायसँग तुलना गरेर सबैभन्दा उपयुक्त छनोट गर्छ — त्यसैले स्पष्ट र विशिष्ट उपकरण विवरण लेख्नु महत्त्वपूर्ण हुन्छ।*

### कार्यान्वयन

स्प्रिंग बुटले घोषणा गरिएको `@AiService` इन्टरफेसलाई सबै दर्ता भएका उपकरणहरूसँग स्वचालित रूपमा जोड्दछ, र LangChain4j ले उपकरण कलहरू स्वचालित रूपमा सञ्चालन गर्छ। पछाडि, एक पूर्ण उपकरण कल प्रयोगकर्ताको प्राकृतिक भाषाको प्रश्नदेखि प्राकृतिक भाषाको जवाफसम्म छेउछाउ छः

<img src="../../../translated_images/ne/tool-calling-flow.8601941b0ca041e6.webp" alt="Tool Calling Flow" width="800"/>

*अन्त-देखि-अन्त प्रवाह — प्रयोगकर्ताले प्रश्न सोध्छ, मोडेलले उपकरण छान्छ, LangChain4j कार्यान्वयन गर्छ, र मोडेल नतिजालाई प्राकृतिक जवाफमा बुन्छ।*

पछाडि, `AiServices` ले जुनसुकै उपकरणका लागि समान उपकरण-कल लूप चलाउँछ — यहाँ एक साधारण `Calculator` साथ उदाहरण देखाइएको छ। तलको सिक्वेन्स डाइग्रामले ठीक के हुन्छ देखाउँछ:

<img src="../../../translated_images/ne/tool-calling-sequence.94802f406ca26278.webp" alt="Tool Calling Sequence Diagram" width="800"/>

*उपकरण-कल लूप — `AiServices` ले तपाईंको सन्देश र उपकरण स्किमा LLM लाई पठाउँछ, LLM ले `add(42, 58)` जस्तो कार्य कल जवाफ दिन्छ, LangChain4j ले `Calculator` मेथड स्थानीय रूपमा चलाउँछ, र नतिजा फिर्ता गर्दै अन्तिम उत्तर दिन्छ।*

### प्रतिक्रिया उत्पादन

मोडेलले मौसम डाटा प्राप्त गर्छ र प्रयोगकर्ताको लागि प्राकृतिक भाषामा प्रतिक्रिया तयार गर्छ।

### वास्तुकला: स्प्रिंग बूट ऑटो-वारिङ

यो मोड्युलले LangChain4j को स्प्रिंग बूट इन्टिग्रेसन प्रयोग गर्छ जुन घोषणा गरिएको `@AiService` इन्टरफेसहरूसँग छ। सुरुमा स्प्रिंग बुटले प्रत्येक `@Component` जुन `@Tool` मेथडहरू समावेश गर्छ पत्ता लगाउँछ, तपाईंको `ChatModel` बीन, र `ChatMemoryProvider` — अनि सबैलाई एउटै `Assistant` इन्टरफेसमा जोड्छ, कुनै बोइलरप्लेट बिना।

<img src="../../../translated_images/ne/spring-boot-wiring.151321795988b04e.webp" alt="Spring Boot Auto-Wiring Architecture" width="800"/>

*@AiService इन्टरफेसले ChatModel, उपकरण कम्पोनेंटहरू, र मेमोरी प्रदायकलाई जोड्छ — स्प्रिंग बुटले पूरै वारिङ स्वचालित रूपमा व्यवस्थापन गर्छ।*

यहाँ पूर्ण अनुरोध जीवनचक्र छ सिक्वेन्स डाइग्राममा — HTTP अनुरोधबाट कन्ट्रोलर, सर्भिस, र ऑटो-वार्ड प्रोक्सी हुँदै, उपकरण कार्यान्वयन सम्म र फिर्तासम्म:

<img src="../../../translated_images/ne/spring-boot-sequence.f83e3d485aa4a3c6.webp" alt="Spring Boot Tool Calling Sequence" width="800"/>

*पूर्ण स्प्रिंग बुट अनुरोध जीवनचक्र — HTTP अनुरोध कन्ट्रोलर र सर्भिसबाट ऑटो-वार्डेड Assistant प्रोसीमा जान्छ, जसले LLM र उपकरण कलहरू स्वचालित रूपमा समन्वय गर्छ।*

यस दृष्टिकोणका मुख्य फाइदाहरू:

- **स्प्रिंग बुट ऑटो-वारिङ** — ChatModel र उपकरणहरू स्वचालित इंजेक्ट गरिएको
- **@MemoryId ढाँचा** — स्वचालित सेसन-आधारित मेमोरी व्यवस्थापन
- **एकल उदाहरण** — Assistant एकपटक सिर्जना गरिन्छ र पुन: प्रयोग गरिन्छ प्रदर्शन सुधारका लागि
- **टाइप-सेफ कार्यान्वयन** — Java मेथडहरू प्रत्यक्ष प्रकार रूपान्तरणसहित कल गरिन्छ
- **बहु-चरण समन्वय** — उपकरण चेनिङ स्वचालित रूपमा ह्यान्डल गर्छ
- **शून्य बोइलरप्लेट** — कुनै म्यानुअल `AiServices.builder()` कल वा मेमोरी ह्यास म्याप आवश्यक छैन

वैकल्पिक दृष्टिकोणहरू (म्यानुअल `AiServices.builder()`) मा बढी कोड चाहिन्छ र स्प्रिंग बूट इन्टिग्रेसन फाइदाहरू मिस हुन्छन्।

## उपकरण चेनिङ

**उपकरण चेनिङ** — उपकरण-आधारित एजेन्टहरूको वास्तविक शक्ति तब प्रकट हुन्छ जब एक प्रश्नले धेरै उपकरणहरू प्रयोग गर्नुपर्छ। "सिएटलको मौसम फर्नहाइटमा कस्तो छ?" सोध्दा, एजेन्टले स्वचालित रूपमा दुई उपकरणहरू जडान गर्छ: पहिले `getCurrentWeather` कल गरेर सेल्सियसमा तापक्रम पाउँछ, त्यसपछि त्यो मान `celsiusToFahrenheit` लाई पास गरेर रूपान्तरण गर्छ — सबै एकै वार्तालाप चरणमा।

<img src="../../../translated_images/ne/tool-chaining-example.538203e73d09dd82.webp" alt="Tool Chaining Example" width="800"/>

*उपकरण चेनिङ क्रियाको अवस्था — एजेन्टले पहिले getCurrentWeather कल गर्छ, त्यसपछि सेल्सियस नतिजा celsiusToFahrenheit मा पठाउँछ, र मिलाइएको उत्तर दिन्छ।*

**सहनशील असफलताहरू** — नकली डाटामा नभएको शहरको मौसम सोध्दा उपकरणले त्रुटि सन्देश फर्काउँछ, र एआईले सहयोग गर्न नसक्ने व्याख्या गर्छ, क्र्यासिंग हुँदैन। उपकरणहरू सुरक्षित रूपमा असफल हुन्छन्। तलको चित्रले दुबै दृष्टिकोणको तुलना गर्छ — सहि त्रुटि ह्यान्डलिङमा एजेन्टले अपवाद समात्छ र सहयोगी प्रतिक्रिया दिन्छ, नभए पूरै एप्लिकेसन क्र्यास हुन्छ:

<img src="../../../translated_images/ne/error-handling-flow.9a330ffc8ee0475c.webp" alt="Error Handling Flow" width="800"/>

*जब उपकरण असफल हुन्छ, एजेन्टले त्रुटि समात्छ र क्र्यास नगरी सहयोगी व्याख्या सहित प्रतिक्रिया दिन्छ।*

यो एकै वार्तालाप चरणमा हुन्छ। एजेन्टले स्वतन्त्र रूपमा धेरै उपकरण कलहरू समन्वय गर्छ।

## एप्लिकेशन प्रयोग गर्दै

एप्लिकेशनले एक वेब इन्टरफेस प्रदान गर्दछ जहाँ तपाईं जलवायु र तापक्रम रूपान्तरण उपकरणहरू पहुँच भएको एआई एजेन्टसँग अन्तरक्रिया गर्न सक्नुहुन्छ। यस्तो देखिन्छ इन्टरफेस — यसमा द्रुत-शुरुवाती उदाहरणहरू र अनुरोध पठाउनको लागि च्याट प्यानल समावेश छ:

### साधारण उपकरण प्रयोग प्रयास गर्नुहोस्

सिधा अनुरोधबाट सुरु गर्नुहोस्: "१०० डिग्री फारेनहाइटलाई सेल्सियसमा रूपान्तरण गर्नुहोस्"। एजेन्टले चिन्ह लगाउँछ कि तापक्रम रूपान्तरण उपकरण आवश्यक छ, त्यसलाई सही प्यारामिटरहरूका साथ कल गर्छ र परिणाम फर्काउँछ। यो कति प्राकृतिक लाग्छ हेर्नुहोस् — तपाईंले कुन उपकरण प्रयोग गर्ने वा कसरी कल गर्ने भन्ने निर्दिष्ट गर्नुभएको थिएन।

### उपकरण श्रृंखला परीक्षण गर्नुहोस्

अब केही बढी जटिल प्रयास गर्नुहोस्: "सिएटलको मौसम कस्तो छ र यसलाई फारेनहाइटमा रूपान्तरण गर्नुहोस्?" एजेन्टले यो कदमहरूमार्फत काम गर्छ। पहिलो मौसम पाउँछ (जसले सेल्सियस फर्काउँछ), यो देख्छ कि फारेनहाइटमा रूपान्तरण गर्न आवश्यक छ, रूपान्तरण उपकरण कल गर्छ, र दुई परिणामहरूलाई एउटै प्रतिक्रिया मा जोड्छ।

### कुराकानी प्रवाह हेर्नुहोस्

च्याट इन्टरफेसले कुराकानी इतिहास कायम राख्छ, जसले तपाईंलाई बहु-पटक अन्तरक्रियाहरू गर्न अनुमति दिन्छ। तपाईं सबै अघिल्ला प्रश्न र प्रतिक्रिया हेर्न सक्नुहुन्छ, यसले कुराकानीलाई ट्र्याक गर्न र कसरी एजेन्टले धेरै आदानप्रदानमा सन्दर्भ निर्माण गर्छ बुझ्न सजिलो बनाउँछ।

<a href="images/tools-conversation-demo.png"><img src="../../../translated_images/ne/tools-conversation-demo.89f2ce9676080f59.webp" alt="वार्तालापमा बहु उपकरण कलहरू" width="800" style="border: 1px solid #ddd; box-shadow: 0 2px 8px rgba(0,0,0,0.1);"/></a>

*साधारण रूपान्तरण, मौसम खोजीहरू, र उपकरण श्रृंखला देखाउँदै बहु-पटकको कुराकानी*

### विभिन्न अनुरोधहरूसँग प्रयोग गर्नुहोस्

विभिन्न संयोजनहरू प्रयास गर्नुहोस्:
- मौसम खोजी: "टोकियोमा मौसम कस्तो छ?"
- तापक्रम रूपान्तरण: "२५°C कति केल्विन हुन्छ?"
- संयुक्त प्रश्नहरू: "पेरिसमा मौसम जाँच्नुहोस् र यदि यो २०°C भन्दा माथि छ भने भन्नुहोस्"

एजेन्टले प्राकृतिक भाषा कसरी व्याख्या गर्छ र उपयुक्त उपकरण कलहरूमा कसरी नक्शा बनाउँछ ध्यान दिनुहोस्।

## प्रमुख अवधारणाहरू

### ReAct ढाँचा (कारण र कार्य)

एजेन्टले कारण (के गर्ने निर्णय) र कार्य (उपकरणहरू प्रयोग गर्ने) बिच बारी-बारीले काम गर्छ। यस ढाँचाले स्वतन्त्र समस्या समाधान सक्षम बनाउँछ, केवल निर्देशनहरूको प्रतिक्रिया मात्र नभई।

### उपकरणको विवरण महत्त्वपूर्ण छ

तपाईंको उपकरणको वर्णनको गुणस्तरले एजेन्टले ती उपकरणहरू कति राम्ररी प्रयोग गर्छ भन्ने प्रत्यक्ष प्रभाव पार्छ। स्पष्ट, विशिष्ट विवरणहरूले मोडेललाई जब र कसरी प्रत्येक उपकरण कल गर्ने बुझ्न मद्दत गर्दछ।

### सत्र व्यवस्थापन

`@MemoryId` एनोटेसनले स्वचालित सत्र-आधारित मेमोरी व्यवस्थापन सक्षम बनाउँछ। प्रत्येक सत्र ID लाई यसको आफ्नै `ChatMemory` इन्स्टेन्स मिल्छ जुन `ChatMemoryProvider` bean द्वारा व्यवस्थापन गरिन्छ, जसले धेरै प्रयोगकर्ताहरूलाई एजेन्टसँग समानान्तर अन्तरक्रिया गर्न अनुमति दिन्छ बिना उनीहरूको कुराकानी मिश्रण हुने। तलको चित्रले देखाउँछ कसरी धेरै प्रयोगकर्ताहरूलाई उनीहरूको सत्र ID अनुसार अलग-अलग मेमोरी स्टोरहरूमा रूट गरिन्छ:

<img src="../../../translated_images/ne/session-management.91ad819c6c89c400.webp" alt="Session Management with @MemoryId" width="800"/>

*प्रत्येक सत्र ID अलग कुराकानी इतिहाससँग मेल खान्छ — प्रयोगकर्ताहरू कहिल्यै अरूका सन्देशहरू देख्दैनन्।*

### त्रुटि व्यवस्थापन

उपकरणहरू असफल हुन सक्छन् — API हरूको समय समाप्त हुन सक्छ, प्यारामिटरहरू अमान्य हुन सक्छन्, बाह्य सेवाहरू बन्द हुन सक्छन्। उत्पादन एजेन्टहरूले त्रुटि व्यवस्थापन आवश्यक हुन्छ ताकि मोडेलले समस्या व्याख्या गर्न वा विकल्पहरू प्रयास गर्न सकून्, सम्पूर्ण एप्लिकेशन क्र्यास नगरोस्। जब उपकरणले अपवाद फ्याँक्छ, LangChain4j ले यसलाई समात्छ र त्रुटि सन्देश मोडेलमा फिडब्याक गर्छ, जसले त्यसपछि प्राकृतिक भाषामा समस्या व्याख्या गर्न सक्छ।

## उपलब्ध उपकरणहरू

तलको चित्रले तपाईंले बनाउन सक्ने उपकरणहरूको व्यापक पारिस्थितिकी देखाउँछ। यस मोड्युलले मौसम र तापक्रम उपकरणहरू देखाउँछ, तर त्यही `@Tool` ढाँचा कुनै पनि Java मेथडमा लागू हुन्छ — डेटाबेस क्वेरीहरूदेखि भुक्तानी प्रक्रिया सम्म।

<img src="../../../translated_images/ne/tool-ecosystem.aad3d74eaa14a44f.webp" alt="उपकरण पारिस्थितिकी" width="800"/>

*कुनै पनि Java मेथड `@Tool` संग एनोटेट गरिएको छ भने AI को लागि उपलब्ध हुन्छ — यो ढाँचा डेटाबेस, API, इमेल, फाइल अपरेसनहरू र अझ धेरैमा फैलिएको छ।*

## कहिले उपकरण आधारित एजेन्टहरू प्रयोग गर्ने

हरेक अनुरोधलाई उपकरणहरू चाहिँदैन। निर्णय यसमा निर्भर गर्दछ कि AI लाई बाह्य प्रणालीहरूसँग अन्तरक्रिया गर्नु आवश्यक छ वा त्यो आफ्नै ज्ञानबाट उत्तर दिन सक्छ। तलको मार्गदर्शकले सारांश गर्छ कहिले उपकरणले मूल्य थप्छ र कहिले आवश्यक हुँदैन:

<img src="../../../translated_images/ne/when-to-use-tools.51d1592d9cbdae9c.webp" alt="कहिले उपकरण प्रयोग गर्ने" width="800"/>

*छिटो निर्णय मार्गदर्शक — उपकरणहरू वास्तविक-समय डाटा, गणना, र कार्यहरूका लागि; सामान्य ज्ञान र सिर्जनात्मक कार्यहरूलाई आवश्यकता छैन।*

## उपकरणहरू बनाम RAG

मोड्युल ०३ र ०४ ले दुबै AI ले के गर्न सक्छ भन्दार विस्तार गर्छ, तर मौलिक रूपमा फरक तरिकाले। RAG ले मोडेललाई **ज्ञान** प्रदान गर्छ दस्तावेजहरू पुन: प्राप्त गरेर। उपकरणहरूले मोडेललाई **कार्यहरू** गर्न अनुमति दिन्छ फंक्शनहरू कल गरेर। तलको चित्रले यी दुई दृष्टिकोणहरू साइड-बाइ-साइड तुलना गर्छ — प्रत्येक कार्यप्रवाह कसरी चल्छ र तिनीहरूबीचको साटासाटहरू:

<img src="../../../translated_images/ne/tools-vs-rag.ad55ce10d7e4da87.webp" alt="उपकरणहरू बनाम RAG तुलना" width="800"/>

*RAG ले स्थिर दस्तावेजहरूबाट जानकारी ल्याउँछ — उपकरणहरूले कार्यहरू कार्यान्वयन गर्छन् र गतिशील, वास्तविक-समय डाटा फेच गर्छन्। धेरै उत्पादन प्रणालीहरूले दुबै संयोजन गर्छन्।*

व्यावहारिक रूपमा, धेरै उत्पादन प्रणालीहरूले दुबै दृष्टिकोण संयोजन गर्छन्: RAG लाई तपाईंको कागजातहरूमा उत्तरहरू आधारभूत बनाउन, र उपकरणहरूलाई प्रत्यक्ष डाटा ल्याउन वा अपरेशनहरू प्रदर्शन गर्न।
